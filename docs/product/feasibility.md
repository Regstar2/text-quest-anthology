# Целесообразность проекта

Срез решения: **27 августа 2026 года**.

Этот документ фиксирует только выводы, влияющие на разработку. Подробное исследование рынка, магазинов, РСЯ и экономики хранится как рабочий исследовательский материал вне репозитория; перед публикацией в конкретном магазине version-sensitive требования повторно проверяются по официальным источникам.

## Решение

**YES, BUT KEEP MVP SMALL.**

Проект стоит делать прежде всего как законченный portfolio/learning product с небольшим финансовым upside. Он не должен планироваться как полноценный бизнес до появления реальной аудитории.

Оценка из исследования:

| Критерий | Оценка |
|---|---:|
| Portfolio project | 8.5/10 |
| Learning project | 9/10 |
| Потенциальный источник небольшого дохода | 3.5/10 |
| Потенциальный полноценный бизнес | 2/10 |
| Риск потратить слишком много времени | HIGH |

## Почему проект оправдан

Один небольшой продукт объединяет несколько реальных инженерных задач:

- React Native и TypeScript;
- Android build/release;
- data-driven branching narrative;
- Ink/inkjs;
- persistence и восстановление состояния;
- интеграцию native advertising SDK;
- архитектурную границу внешнего провайдера;
- signing/versioning;
- store moderation;
- поддержку опубликованного приложения.

Для портфолио критически важно именно завершить публикацию. Незаконченный универсальный framework даёт меньше ценности, чем маленькое приложение, прошедшее реальный release cycle.

## Рынок

Исследование подтверждает, что mobile interactive fiction остаётся живой, но нишевой категорией. Существуют долгоживущие проекты с крупной lifetime-аудиторией, однако свежие отдельные текстовые игры могут получать значительно меньший трафик.

Следствия для проекта:

- одна качественная история достаточна для проверки MVP;
- одна история недостаточна для долгосрочного retention;
- новые истории нельзя писать заранее только ради слова «антология»;
- отсутствие большого числа конкурентов не считается доказательством большого свободного рынка;
- визуальная аккуратность обязательна, полноценная VN-графика — нет.

## Финансовая гипотеза

Реклама рассматривается как эксперимент, а не как release success criterion.

Исследование не обнаружило официального фиксированного eCPM РСЯ для такого жанра, поэтому любые оценки дохода являются sensitivity model, а не прогнозом.

Практическая шкала для первого небольшого продукта:

- `0–500 ₽/месяц` — нормальный результат MVP;
- `500–3 000 ₽/месяц` — хороший результат;
- `3 000–10 000 ₽/месяц` — очень хороший результат и дополнительный аргумент в пользу новых историй;
- `10 000+ ₽/месяц` — успех, но не исходная цель;
- `50 000 ₽/месяц` — не использовать как business case первого релиза.

Почти нулевой доход не означает провал, если portfolio/learning цели достигнуты.

## Юридический статус

Для первого бесплатного приложения с рекламой текущего статуса самозанятого достаточно по выводам исследования:

- RuStore допускает публикацию и рекламную монетизацию без RuStore Billing;
- РСЯ работает с российскими самозанятыми;
- ИП не требуется только ради рекламного MVP.

Переход к ИП рассматривается только при фактическом решении добавить store billing: paid stories, premium, remove ads, subscription или другой цифровой entitlement.

Перед подключением платёжной модели требования магазина и налоговая схема проверяются заново.

## Приоритет магазинов

Порядок после готовности стабильного Android release:

1. **RuStore** — первый обязательный магазин.
2. **Huawei AppGallery** — наиболее логичный второй магазин после проверки MVP.
3. **Xiaomi GetApps** — третий, после фактической проверки onboarding.
4. **Google Play** — только если developer account и все необходимые операции реально доступны.
5. **GitHub Releases** — дополнительный APK mirror, не основной discovery channel.

Samsung/Amazon и малые альтернативные stores не входят в ранний scope.

## Multi-store принцип

Приложение не должно знать, откуда оно установлено, если это не нужно конкретной функции.

Базовые правила:

- narrative core не зависит от магазина;
- Yandex SDK не импортируется в reader/narrative code;
- первый ads provider — Yandex, но контракт допускает `NoAdsProvider`;
- один package name сохраняется между каналами, если это возможно;
- разработчик владеет Android signing key и хранит резервные зашифрованные копии;
- store-specific рекламные placement IDs и конфигурация находятся на границе distribution/ads, а не в story logic;
- Gradle flavors не создаются заранее: они вводятся только при добавлении второго магазина, если реально нужны.

## Decision gate после MVP

После первого RuStore-релиза не начинается автоматическая разработка второй истории.

### CONTINUE

Продолжать content development, если есть минимум два содержательных сигнала, например:

- 150–300+ реальных установок без существенной платной закупки;
- минимум 5 содержательных положительных отзывов/сообщений;
- пользователи прямо просят следующую историю;
- появился заметный, пусть небольшой рекламный доход;
- проект остаётся полезным для портфолио/собеседований;
- автору всё ещё интересно производить narrative content.

### MAINTENANCE

Если приложение стабильно и опубликовано, но аудитория мала, оставить его законченным portfolio project и исправлять только существенные дефекты/совместимость.

### PIVOT

Если установки есть, но отзывы повторяют одну проблему — реклама, темп, слабые выборы, неудобный reader — исправить эту проблему до производства дополнительного контента.

### ARCHIVE

Если после разумного распространения почти нет установок/обратной связи, а portfolio/learning цели уже достигнуты, прекратить content development без удаления готового проекта.

## Главный stop rule

Failure case проекта — не `0 ₽`.

Failure case — **потратить месяцы на платформу, не выпустив «Завалинку»**.
